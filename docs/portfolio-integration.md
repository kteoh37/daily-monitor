# Automatic Japan portfolio report

The public report is `public/reports/japan-portfolio/index.html`, linked as **Japan flows**. Approved export contract: `index.html`, `manifest.json`, `portfolio_flows.png`, `portfolio_flows_recent.png`, `jsda/rolling_jgb_purchases.png`. The audit rejects all other files and unexpected manifest fields. No raw Haver Parquets/metadata, source CSVs, interactive JSDA HTML, credentials or full tracker state are published.

The existing daily-monitor deployment workflow owns refresh/publication. Its single commit-pinned Haver checkout supplies daily dashboard series, policy-report data and monthly JSDA series. MOF is downloaded live from the official HTTPS endpoint. Reviewed parser/calculation code is adapted from `kteoh37/japan-portfolio-tracker`; no cross-repo tracker access, extra credential, private tracker schedule or ChatGPT task change is required.

MOF preserves January 2022 and January 2026 cumulative baselines, allocating full weeks by week-end date. JSDA preserves rolling five CALENDAR months, five named sectors plus a separate overall total, medium-/long-/super-long-term coupon JGB groups, yen trillion, nominal/face value, excluding Treasury bills and discount bonds. Overall totals include other categories and cannot be inferred by summing the five sectors. Transactions do not identify same-investor repatriation.

Every refresh stages each complete component before promotion. Failures preserve all of that component's last good PNGs/descriptions and display a failed/stale warning with separate attempt and last-success timestamps. Partial updates can deploy the warning but mark the workflow failed afterward. Source regression, invalid units/frequency and missing rolling-window months are rejected. MOF older than 21 days or JSDA older than 75 days is flagged stale; unchanged inputs still show observation age.

Durable sanitized manifest stores dates, source SHA/vintage, approved current-magnitude prose, last check status, one whole-history fingerprint per component, new-period count and prior-history-revised flag. On the next run the source prefix through the previous latest date is rehashed to detect revisions without storing public observation histories. Initialization establishes a comparison baseline; it never claims all historical observations are newly released. A partial failure preserves the previous fingerprint so subsequent revision checks remain valid.

The workflow commits ONLY the explicit five-file export using the platform's existing ephemeral GITHUB_TOKEN and deploys that same working tree. Dashboard/policy JSONs are generated directly in the build, never committed from raw snapshots. Ordinary token-authored commits do not recursively trigger push workflows. Main branch updates are non-force pushes; concurrent changes cause a safe failure, not overwrites. Existing HAVER_DATA_TOKEN already accesses the Haver repository and is reused in its existing checkout; no secret value/scope is read or changed.

Daily dashboard cadence stays 13:00/22:00 UTC. Weekly portfolio cron is enabled only after a successful manual live cloud run. Two UTC candidates plus an America/New_York hour/day gate preserve Thursday 10:00 across daylight saving time, with the wrong-hour run skipped. GitHub cron is best effort and can run late. Manual refresh remains available with workflow_dispatch `refresh_portfolio=true`.
